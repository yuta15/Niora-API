# 0002: 優先するアーキテクチャ特性を決定する

## 背景

Niora APIのアーキテクチャを決定する前に、機能要件とは別に、設計全体で何を重視するかを明確にする必要がある。

このプロジェクトは1人で開発・運用し、インフラと外部サービスは可能な限り無料枠を利用する。また、WorkspaceではOSコマンドを実行できるため、k3s基盤や別のWorkspaceへの意図しないアクセスに注意する必要がある。

一方、v0.0.1はローカルまたはアクセスを制限した環境で利用し、一般公開や多数の同時利用を対象としない。

## 決定

次のアーキテクチャ特性を優先する。

1. セキュリティ
2. コスト効率
3. 単純性と開発効率

セキュリティは必須の制約として扱い、コストや開発速度を理由に必要な対策を省略しない。安全性を満たす選択肢の中から、継続コスト、実装するコード量、コンポーネント数、運用作業が小さいものを選ぶ。

v0.0.1では、可用性、可観測性、スケーラビリティ、性能を主要なアーキテクチャ判断の軸にしない。ただし、環境の起動・接続・削除と失敗原因を確認できる最低限のログは実装する。

一般公開、複数利用者、複数Workspaceの同時実行へ進む前に、アーキテクチャ特性の優先順位を見直す。

## 代替案

- 可用性を優先し、初期段階から冗長化と無停止運用を設計する
- 可観測性を優先し、メトリクス、分散トレーシング、アラート基盤を導入する
- 将来の拡張性を優先し、初期段階から複数の実行基盤や接続方式を抽象化する
- 開発作業を減らすため、コストが高くてもマネージドサービスを優先する

## 影響

- セキュリティ上必要な実装は、コード量や作業時間が増えても省略できない
- 無料枠とk3sを活用し、継続的なインフラ費用を抑える方向で設計する
- v0.0.1に不要なコンポーネント、抽象化、運用基盤を追加しない
- 冗長化を行わないため、障害やメンテナンスによる一時停止を許容する
- 高度な監視を導入しないため、問題調査の一部を手動で行う必要がある
- 将来の要件によっては、可用性、可観測性、スケーラビリティを高めるための設計変更が必要になる
