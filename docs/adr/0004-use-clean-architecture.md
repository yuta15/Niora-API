# 0004: ソフトウェア構成にクリーンアーキテクチャを採用する

## 背景

Niora APIは、k3sを利用したUbuntuのWorkspaceだけでなく、将来はデータベースやHTTPサービスなど、異なる種類の環境と接続方式を扱う。外部システムごとのAPI、接続手順、データ形式の差をNiora API内で吸収し、利用者には同じドメイン概念として提供する必要がある。

k3s、データベース、外部認証、Workspaceへの接続方式は、要件や運用環境の変化によって差し替える可能性がある。ドメインとユースケースが特定の外部技術へ直接依存すると、差し替えの影響がアプリケーション全体へ広がる。

また、Niora APIはモジュラーモノリスとして構成するため、単一のアプリケーション内でもドメインごとの責務と依存関係を明確に分ける必要がある。

## 決定

Niora APIのソフトウェア構成にクリーンアーキテクチャを採用する。

モジュラーモノリスの内部を、少なくとも次のドメインモジュールに分割する。

- `Workspace`：WorkspaceDefinition、Workspaceのライフサイクル、接続を扱う
- `Auth`：外部認証との連携、Niora内部の利用者、権限を扱う
- `Textbook`：教科書と章を扱う

各モジュール内では、次の依存性ルールを適用する。

- DomainはApplication、FastAPI、データベース、k3s、外部サービスへ依存しない
- ApplicationはDomainに依存し、ユースケースを実装する
- InboundはAPIを基本とし、API AdapterからApplicationのユースケースを呼び出す
- 期限切れWorkspaceを削除するScheduled Jobは、例外として専用のInbound Adapterから同じApplicationの削除ユースケースを呼び出す
- Applicationが必要とする外部操作は、Application側のPortとして定義する
- k3s、データベース、外部認証、各種接続方式をAdapterとして実装する
- AdapterはApplicationのPortとDomainの型に依存する
- Adapterの組み立てはアプリケーション起動時に行う
- モジュール間は、相手モジュールの内部実装やデータへ直接依存せず、公開されたApplicationインターフェースを利用する

PortとAdapterは、差し替えの可能性がある外部境界に対して作成する。モジュール内部のすべてのクラスや関数を抽象化の対象にはしない。

## 代替案

### 外部技術へ直接依存するレイヤードアーキテクチャ

Applicationからk3sクライアントやデータベース実装を直接呼び出す案。

初期のコード量は少なくなるが、外部技術を差し替える際にユースケースやドメインへ変更が広がるため採用しない。

### 技術レイヤー単位での分割

アプリケーション全体を`controllers`、`services`、`repositories`などの技術レイヤーだけで分割する案。

ドメインが増えると、Workspace、Auth、Textbookの変更が同じパッケージ内へ混在し、モジュール境界が不明確になるため採用しない。

### すべてをPortとして抽象化する

内部処理を含むすべての依存関係にInterfaceを定義する案。

差し替える必要がない箇所にも抽象化と実装が必要になり、個人開発に対してコード量と作業量が大きくなるため採用しない。

## 影響

- k3sやデータベースなどの外部技術をAdapterの変更で差し替えやすくなる
- テスト時にPortの代替実装を利用し、外部システムなしでユースケースを検証できる
- DomainとApplicationを外部ライブラリのデータ型やライフサイクルから独立させられる
- Workspace、Auth、Textbookごとに変更の影響範囲を限定しやすくなる
- Domain、Application、Port、Adapterの間でデータを変換するコードが必要になる
- Portの定義や依存関係の組み立てに追加のコードが必要になる
- モジュール境界と依存方向を継続して確認しないと、形式だけのクリーンアーキテクチャになる
