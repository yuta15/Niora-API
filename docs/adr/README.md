# アーキテクチャ決定記録（ADR）

Niora APIのアーキテクチャ上の重要な意思決定を記録します。

決定済みのADRは[決定記録一覧](decisions.md)で管理します。

## 記録する粒度

ADRには、Architectureや実装全体へ継続的に影響する意思決定と、その判断理由を記録します。後から読んだ人が、
現在の方式を選んだ理由、採用しなかった選択肢、変更時に再評価すべき影響を理解できる粒度にします。

ADRへ記録する内容は次のとおりです。

- 解決する問題と判断が必要になった背景
- 採用する方式、責務の境界、依存方向などの重要な制約
- 採用理由と、検討した主な代替案を採用しなかった理由
- 決定によって生じる利点、欠点、実装や運用への影響

次の内容は詳細設計や手順書として関連ドキュメントへ記録し、ADRには原則として含めません。

- Class、Function、Directoryなどの具体的な実装構造
- 環境変数名、接続プール数、Timeoutなどの個別設定値
- 開発コマンド、Migrationコマンド、デプロイ手順
- Manifest、Fixture、例外変換などの実装詳細
- テストデータの作成、分離、後始末の具体的な方法

ADRには方式と境界を記録し、現在有効な設定と手順は、それぞれの責務を持つドキュメントを正とします。

| ADRへ記録する内容 | 関連ドキュメントへ記録する内容 |
| --- | --- |
| Database SchemaにSQLAlchemyを採用する | Table、Column、Indexの定義 |
| Transaction境界をUseCaseとする | Unit of WorkとRepositoryの具体的な構成 |
| MigrationにAlembicを採用する | Revision作成・適用コマンドとデプロイ手順 |
| Integrationテストで実際のMySQLを使用する | Containerの起動、Database分離、後始末の手順 |

1つのADRでは、同じ背景と目的を持ち、まとめて変更・再評価される意思決定を扱います。独立して変更される可能性が高い判断は、
別のADRへ分けます。詳細を除いた結果、採用した方式と理由を説明できなくなる場合は、判断に必要な範囲だけADRへ残します。

## ファイル名

連番と短いタイトルを使用します。

```text
0001-define-version-0.0.1-scope.md
0002-prioritize-architecture-characteristics.md
```

## テンプレート

```markdown
# 0001: タイトル

## 背景

判断が必要になった背景や制約を記載します。

## 決定

採用する方針を記載します。

## 代替案

検討したほかの選択肢を記載します。

## 影響

決定によって生じる利点、欠点、制約を記載します。

## 関連ドキュメント

必要な場合に、現在の詳細設計や手順を管理するドキュメントへのLinkを記載します。
```
