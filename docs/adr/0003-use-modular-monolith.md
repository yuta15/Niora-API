# 0003: 全体構成にモジュラーモノリスを採用する

## 背景

Niora APIは、登録済みの教科書と章の提供、Workspaceの起動・管理、Workspaceへの接続を行う必要がある。教科書やWorkspaceDefinitionはデータベースで管理し、Workspaceの実行状態はk3sから取得する。

これらの責務を独立したサービスとして分離するか、1つのアプリケーション内にまとめるかを決定する必要がある。

このプロジェクトは1人で開発・運用する。優先するアーキテクチャ特性はセキュリティ、コスト効率、単純性と開発効率であり、v0.0.1では可用性やスケーラビリティを主要な判断軸にしない。

## 決定

Niora APIをモジュラーモノリスとして構成する。

- Niora APIを単一のコードベースとビルド成果物として開発・デプロイする
- 利用者からの教科書閲覧、Workspaceの起動・管理、Workspaceへの接続をNiora APIの入口へ集約する
- アプリケーション内部を`Textbook`モジュールと`Workspace`モジュールの責務で分離する
- Workspaceへの接続はNiora APIが中継する
- 各モジュールは同じデータベースを利用するが、担当するデータの所有境界を分ける
- Workspaceモジュールだけがk3sを操作する
- モジュール間の連携は、ネットワーク通信ではなくアプリケーション内部のインターフェースを使用する
- APIと期限切れ削除Jobは、同じWorkspaceモジュールのApplicationユースケースを利用する

ドメインモジュールを独立したサービスとしてデプロイしない。APIと期限切れ削除Jobは実行プロセスが分かれるが、同じビルド成果物とApplicationユースケースを利用する。将来分離する必要が生じた場合に備え、モジュール内部の実装やデータへ別モジュールから直接依存しないようにする。

## 代替案

### マイクロサービス

教科書管理、Workspace管理、Workspace接続を独立したサービスとして構成する案。

独立したデプロイやスケーリングが可能になる一方、サービス間通信、認証、障害処理、デプロイ、ログ監視などの仕組みが追加で必要になる。1人で開発・運用する現状では、開発コストと運用コストが高すぎるため採用しない。

### 境界を設けないモノリス

すべての機能を1つのアプリケーションにまとめ、内部モジュールの責務を明確に分けない案。

初期実装は容易だが、教科書とWorkspaceの責務や依存関係が混在し、変更の影響範囲が大きくなるため採用しない。

## 影響

- ビルド成果物と運用するアプリケーションを1つに抑えられる
- モジュール間でネットワーク通信や分散トランザクションを実装する必要がない
- 1つのデータベースを利用するため、初期のデータ管理とトランザクションを単純にできる
- モジュール境界を保つため、コード上の依存方向とデータ所有を継続して確認する必要がある
- Niora API全体をまとめてデプロイするため、モジュール単位の独立したリリースはできない
- Workspace接続の負荷が増えた場合、Niora API全体に影響する可能性がある
- 将来、特定の責務だけを独立してスケールまたはデプロイする必要が生じた場合は、サービス分離を再検討する
