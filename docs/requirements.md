# 要件

Niora APIで実現する内容と、設計・実装時に考慮する制約を整理します。

## 目的

### 解決する問題

- Ubuntu環境、データベース、各種サービスを検証するには、事前の環境構築が必要になる
- 環境構築やインフラに関する前提知識が、サービスを試すまでの障壁になる
- 環境構築を終えるまで、対象の技術やサービスで何ができるのかを確認できない
- 教科書などの教材と実環境を組み合わせて学習するための準備に手間がかかる

### 提供する価値

- インフラや各種サービスを、環境構築の負担を抑えて気軽に検証できる
- 自分で環境を構築する前に、対象の技術やサービスで何ができるのかを体験できる
- 教科書などの教材と併用し、実際に操作しながらインフラ技術を学習できる
- 教材投稿者が、教科書や教材の内容と対応する検証環境を定義して提供できる
- 学習者が、教材と検証環境を行き来せず、一体化された学習体験を得られる

### 成功と判断する基準

#### サービスとしての成功

- 複数人の利用者に実際に利用してもらう

#### 個人プロジェクトとしての成功

- 業務レベルを意識したアーキテクチャを設計する
- 設計内容と判断理由を言語化・可視化する
- 設計内容を第三者へ伝えられる状態にする

## 利用者

| 利用者 | 目的 | 備考 |
| --- | --- | --- |
| 教材投稿者 | 教科書や教材と紐付いた検証環境を定義し、学習者へ提供する | 教材の作成者や提供者を想定する |
| 学習者 | 教材の内容に対応した環境を使い、実際に操作しながら学習する | 環境構築前の試用も含む |

## 主要ユースケース

| ID | 利用者 | やりたいこと | 期待する結果 |
| --- | --- | --- | --- |
| UC-001 | 教材投稿者 | 教材を管理する | 教材の作成、更新、公開状態の変更ができる |
| UC-002 | 教材投稿者 | 教材の章ごとに学習環境を定義する | 各章の内容に対応した環境を学習者へ提供できる |
| UC-003 | 学習者 | 教材の章に対応する学習環境を起動する | 環境構築の負担なく検証を開始できる |
| UC-004 | 学習者 | 学習環境のOSへログインする | OS上で教材に沿ったコマンドを実行できる |
| UC-005 | 学習者 | 学習環境のデータベースへ直接接続する | SQLを実行してデータベースを検証できる |
| UC-006 | 学習者 | 学習環境で稼働するHTTPサービスへアクセスする | Nginxなどのサービスの動作を確認できる |
| UC-007 | 利用者 | 外部の認証サービスを利用してログイン・ログアウトする | 本人として安全にサービスを利用・終了できる |

## 機能要件

| ID | 機能 | 内容 |
| --- | --- | --- |
| FR-001 | 章単位の学習環境設定 | 教材投稿者は、教材の章ごとに異なる学習環境を設定できる |
| FR-002 | 教材管理 | 教材投稿者は、教材の作成、更新、公開状態の変更ができる |
| FR-003 | 学習環境の起動 | 学習者は、教材の章に対応する学習環境を起動できる |
| FR-004 | 学習環境へのOSアクセス | 学習者は、起動した学習環境のOSへログインしてコマンドを実行できる |
| FR-005 | 学習環境へのデータベースアクセス | 学習者は、起動した学習環境のデータベースへ直接接続してSQLを実行できる |
| FR-006 | 学習環境へのHTTPアクセス | 学習者は、起動した学習環境で公開されたHTTPサービスへアクセスできる |
| FR-007 | 外部認証連携 | 利用者は、外部の認証サービスを利用してログイン・ログアウトできる |
| FR-008 | 利用者の対応付け | 外部サービスで認証された利用者を、Niora内部の利用者と一意に対応付けられる |
| FR-009 | 権限制御 | 利用者の役割とリソースの所有関係に基づき、教材と学習環境へのアクセスを制御できる |

## 非機能要件

### セキュリティとプライバシー

- 利用者の認証は外部の認証サービスへ委譲し、Nioraではパスワードを保持しない
- 外部の認証サービスから受け取った認証結果の正当性を検証する
- 利用者は、権限のない教材や学習環境を操作できない
- 利用者ごとの情報と学習環境を分離する


## 制約事項

## コスト制約
- 個人開発のため開発・運用コストが限られている
- 個人開発のため金銭的リソースが限られている

## セキュリティ制約
- 他ユーザーの環境に入れないなど世間一般的に必要とされるセキュリティを満たす必要がある。なお、決済などが含まれるわけではないので高度なセキュリティ要件があるわけではない

## その他制約
- 学習的な意図もあるため、オブジェクト指向での実装に制限し簡単なスクリプトでリリースを優先するなどは行わない。
- 個人で継続的に開発・運用していける範囲内で丁寧に作る。
